# ТЗ → OpenAPI 3.0.3

Отдельный сервис. Он не входит в RAG и не ищет по индексу: на вход приходит полный текст технического задания, на выход — YAML OpenAPI 3.0.3 и отчёт о пробелах.

Большое ТЗ не отправляется в модель целиком. Если заданы `OPENAPI_VLLM_BASE_URL` и `OPENAPI_VLLM_MODEL`, модель по окнам находит границы фрагментов и для каждого принятого фрагмента пишет YAML OpenAPI 3.0.3. Код проверяет, что цитаты границ есть в окне, сшивает `paths` и одинаковые схемы и проверяет сборку пакетом `openapi-spec-validator`. Без vLLM остаётся прежний разбор уже известных таблиц: новый документ в `paths` не попадает, в отчёте остаётся вопрос.

## Что сделать один раз

```powershell
cd c:\Technokratos\openapi-from-spec
python -m venv .venv
.\.venv\Scripts\python -m pip install -e .
```

Проверка примера без модели:

```powershell
.\.venv\Scripts\openapi-from-spec examples\account-balances.txt -o out\account-balances.yaml --report out\report.json --title "Счета"
```

Страница для вставки текста: `openapi-from-spec --serve`, затем открыть `http://127.0.0.1:8090`. Адрес vLLM задаётся на сервере, не в браузере.

```powershell
$env:OPENAPI_VLLM_BASE_URL = "http://127.0.0.1:8000/v1"
$env:OPENAPI_VLLM_MODEL = "имя-модели"
$env:OPENAPI_VLLM_API_KEY = "ключ-если-нужен"
.\.venv\Scripts\openapi-from-spec --serve
```

`OPENAPI_VLLM_BASE_URL` уже содержит `/v1`. Префикс `/api/v1` (`OPENAPI_PATH_PREFIX`) применяет только кодовый разбор без модели.

## Как режется документ

С моделью:

1. Код режет текст окнами около 12 000 символов с перекрытием. Окно не обязано совпадать с методом. Если разрез попал в таблицу, шапка повторяется в следующем окне.
2. Модель возвращает дословные цитаты начала и конца. Цитата, глагол HTTP или имя принимаются, только если они есть в этом окне.
3. На каждый принятый фрагмент уходит отдельный запрос: модель возвращает YAML только его операций. Остальной файл в этот запрос не входит.
4. Код складывает `paths`. Одинаковые `components/schemas` получают один `$ref`. Конфликт имён остаётся в отчёте.
5. Сборка проверяется по схеме OpenAPI 3.0.3. Текст ошибки один раз возвращается модели вместе с её YAML и тем же фрагментом. Второй неуспех остаётся в отчёте, черновой YAML сохраняется.

Без модели код по-прежнему узнаёт строку `GET accountBalances`, заголовок перед «Параметры запроса» и глагол внутри абзаца. Ответы 400, 401, 404 и 500 в этом режиме добавляет компилятор и помечает `x-origin: skill-template`. Схему авторизации сервис не выдумывает.

## Скилл для модели без интернета

Рабочая инструкция, которую сервис и так вставляет в системный запрос:

- `src/openapi_from_spec/skill/SKILL.md`

Задачи в системном запросе: `segment` и `openapi`. Правила формы для `openapi` дописываются из `skill/knowledge/openapi-3.0.3.md`. Дополнительно в базу знаний модели можно положить ту же папку `skill/`:

- `skill/knowledge/openapi-3.0.3.md` — короткий контракт 3.0.3 для YAML одного фрагмента
- `skill/knowledge/type-mapping.md` — перевод типов ТЗ

Эти файлы не ссылаются на сеть. Поиск по базе знаний не заменяет системный запрос: сервис передаёт скилл вместе с одним фрагментом, потому что фрагмент обязан подчиняться правилам, а не случайно найденному куску.

Проверки: `python -m unittest discover -s tests`.
