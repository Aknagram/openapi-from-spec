# ТЗ REST API магазина. Длинные методы

Три метода одного сервиса. Базовый адрес: `https://api.shop.example`. Имя API: `public`, версия: `v1`.

Общие соглашения:

- Идентификаторы — UUID.
- Деньги — целые числа в минимальных единицах валюты (копейки для RUB).
- Время — строка timestamp в UTC.
- Заголовок `Authorization` необязателен для чтения заказа и обязателен для создания и смены статуса. Схему авторизации этот документ не задаёт.
- Коды, которых нет в описании метода, не входят в контракт.

---

## Метод GET /orders/{orderId} — получить заказ

### Общее описание

Метод возвращает полную карточку заказа: покупателя, доставку, состав, оплату и итоги. Его вызывает экран заказа в личном кабинете и служба поддержки, когда оператор открывает заказ по номеру из обращения.

Заказ читают и авторизованный покупатель, и сотрудник поддержки. Неавторизованный вызов допустим только если в запросе передан одноразовый токен просмотра в заголовке `X-View-Token`. Если нет ни авторизации, ни токена, метод всё равно может вернуть заказ, но без полей `customer.phone`, `customer.email` и `payment.panMask`. Ошибки из-за отсутствия авторизации нет.

Покупатель видит только свой заказ. Сотрудник поддержки видит любой заказ. Проверка владельца выполняется по идентификатору пользователя из авторизации и полю `order.customer_id`. Если заказ принадлежит другому покупателю, ответ такой же, как если бы заказа не было: HTTP 404 и сообщение «Заказ не найден». Так метод не сообщает, что чужой идентификатор существует.

### Доступы и ограничения

- Покупатель читает свой заказ.
- Сотрудник поддержки читает любой заказ.
- Гость с `X-View-Token` читает заказ без контактов и маски карты.
- Заказ в статусе `draft` гостю не отдаётся: HTTP 404 «Заказ не найден».

### Запрос

Method type: GET BaseURL: https://api.shop.example API name: public API version: v1 Method name: orders/{orderId}

Заголовки общие для системы. Отдельных обязательных заголовков у метода нет. Query-параметров нет. Тела запроса нет.

Пример запроса:

1 GET https://api.shop.example/public/v1/orders/{orderId}

Пример с конкретным идентификатором:

1 GET https://api.shop.example/public/v1/orders/6b1f4c2a-9d0e-4a11-8c33-1a2b3c4d5e6f

### Пример ответа — успех

Код HTTP: 200

Тело ответа содержит объект заказа. Пример ниже сокращён: полный состав полей задаёт таблица маппинга, а не этот пример. Если пример и таблица расходятся, верна таблица.

```json
{
  "id": "6b1f4c2a-9d0e-4a11-8c33-1a2b3c4d5e6f",
  "number": "A-10442",
  "status": "paid",
  "customer": {"id": "c0ffee00-0000-4000-8000-000000000001", "name": "Анна Смирнова"},
  "items": [{"sku": "MUG-01", "name": "Кружка", "quantity": 2, "price": 89000}],
  "totals": {"goods": 178000, "delivery": 35000, "discount": 0, "total": 213000}
}
```

### Пример ответа — не найдено

Заказ не найден, скрыт как черновик или принадлежит другому покупателю.

Код HTTP: 404

Тело ответа:

```json
{"errorMessage": "Заказ не найден"}
```

### Пример ответа — неверный формат запроса

Если `orderId` не UUID, запрос не обрабатывается.

Код HTTP: 400

Тело ответа:

```json
{"errorMessage": "Неверный формат идентификатора заказа"}
```

### Пример ответа — сервис недоступен

Код HTTP: 503

Тело ответа:

```json
{"errorMessage": "Сервис временно недоступен"}
```

### Основной сценарий

1. Получить `{orderId}` из пути.
2. Если значение не UUID, вернуть HTTP 400 «Неверный формат идентификатора заказа».
3. Найти заказ в таблице `order` по `order.id`. Если записи нет, вернуть HTTP 404 «Заказ не найден».
4. Если статус заказа `draft` и вызывающий не сотрудник поддержки, вернуть HTTP 404 «Заказ не найден».
5. Если вызывающий — покупатель и `order.customer_id` не совпадает с пользователем из авторизации, вернуть HTTP 404 «Заказ не найден».
6. Собрать покупателя из `customer`, доставку из `delivery`, позиции из `order_item` и `product`, оплату из `payment`, итоги из колонок `order`.
7. Если нет авторизации и нет `X-View-Token`, не включать `customer.phone`, `customer.email` и `payment.panMask`. Остальные поля вернуть.
8. Вернуть HTTP 200 и объект заказа.

### Правила, которые нельзя сократить

Номер заказа `number` — человекочитаемый код вида `A-10442`. Его показывают в интерфейсе и в письме. В пути запроса его нет: путь всегда содержит UUID. Номер не уникален между стендами, уникален `id`.

Статус заказа — одно из значений `draft`, `created`, `paid`, `assembling`, `shipped`, `delivered`, `cancelled`. Метод не пересчитывает статус. Он возвращает значение колонки `order.status` как есть. Пустая строка в этой колонке — ошибка данных, метод всё равно отдаёт поле и пишет предупреждение в журнал. Клиенту об ошибке данных отдельным кодом не сообщают.

Дата создания `createdAt` берётся из `order.created_at` и отдаётся как timestamp. Дата оплаты `paidAt` берётся из `payment.paid_at`. Если оплаты ещё не было, `paidAt` равен `null`, поле в ответе присутствует. Так клиент отличает «ещё не оплачен» от «поле забыли».

Покупатель — объект. `customer.id` — UUID из `customer.id`. `customer.name` — склейка `customer.last_name`, пробела и `customer.first_name`. Если фамилии нет, остаётся имя без ведущего пробела. `customer.email` и `customer.phone` отдаются только авторизованному вызывающему или держателю `X-View-Token`. Гостю без токена эти два поля отсутствуют в JSON, а не приходят пустыми строками.

Доставка — объект. `delivery.method` — `courier` или `pickup`. `delivery.city` и `delivery.address` обязательны для курьера. Для самовывоза `delivery.address` — адрес пункта выдачи, `delivery.postalCode` может быть `null`. `delivery.comment` — комментарий курьеру, необязательное поле, максимум 500 символов в исходных данных, в JSON отдаётся как есть, без обрезки на чтении.

Позиции `items` — массив. Пустой массив допустим только у черновика, а черновик этому методу почти не виден. Если у видимого заказа нет позиций, это порча данных: вернуть пустой массив и HTTP 200, в журнал — ошибка. Элемент массива: `items[].id` — UUID строки `order_item.id`, не идентификатор товара. `items[].sku` — артикул. `items[].name` — название на момент заказа, колонка `order_item.product_name`, а не текущее имя из каталога. `items[].quantity` — целое больше нуля. `items[].price` — цена одной единицы в минимальных единицах валюты на момент заказа. Скидка на позицию в эту цену уже не входит: скидка лежит в итогах.

Оплата — объект. `payment.method` — `card` или `invoice`. `payment.amount` совпадает с `totals.total`. Если не совпадает, метод не чинит данные и отдаёт оба числа как в базе. `payment.currency` — трёхбуквенный код, для этого контура всегда `RUB`. `payment.panMask` — последние 4 цифры карты с маской, только для авторизованного вызывающего. Для счёта `panMask` равен `null`. `payment.paid` — булево, истинно когда `payment.paid_at` заполнен.

Итоги — объект и обязателен всегда. `totals.goods` — сумма `price * quantity` по позициям. `totals.delivery` — стоимость доставки, ноль если самовывоз. `totals.discount` — скидка по промокоду, ноль если промокода не было. `totals.total` — `goods + delivery - discount`. Отрицательный итог в базе метод не исправляет.

Комментарий покупателя `comment` необязателен. Если в базе `null`, в JSON тоже `null`.

Поле `loyaltyPoints` в таблице маппинга помечено как будущее: программа лояльности ещё не заведена. Поле всё равно входит в ответ и пока всегда `null`. Задачу на таблицу баллов заводят отдельно, из контракта этого метода поле не убирают.

### Проверки чтения, которые остаются в контракте

Идентификатор в пути сравнивается с каноническим текстовым UUID: 8-4-4-4-12 шестнадцатеричных знаков, дефисы обязательны. Верхний и нижний регистр равноправны. Фигурные скобки вокруг значения клиент не передаёт: скобки в этом документе только обозначают параметр. Пробелы по краям не обрезаются, строка с пробелом — HTTP 400.

Токен `X-View-Token` ищется в таблице `order_view_token`. Срок действия — 72 часа с `order_view_token.created_at`. Просроченный токен не даёт прав гостя: метод ведёт себя так, будто заголовка не было, и скрывает почту, телефон и маску карты. Неверный токен не отличается от отсутствующего, отдельного кода для него нет.

Скрытие полей делается на сборке JSON, а не затиранием в базе. Для гостя без токена ключи `customer.email`, `customer.phone` и `payment.panMask` отсутствуют. Для авторизованного покупателя своего заказа и для поддержки они присутствуют. У поддержки `payment.panMask` есть даже если заказ оплачен счётом: тогда значение `null`.

Имя покупателя собирается в момент ответа, а не хранится готовой строкой. Двойные пробелы между фамилией и именем схлопываются в один. Если и фамилия, и имя пустые, `customer.name` — пустая строка, поле всё равно есть: обязательность в таблице означает ключ в JSON, а не непустое значение.

Цена и суммы не пересчитываются из каталога при чтении. Каталог мог изменить цену после создания заказа. Чтение всегда отдаёт снимок в `order_item` и в колонках итогов. Расхождение снимка с текущим каталогом в ответ не выносится.

Сортировка `items` — по `order_item.position`, затем по `order_item.id`. Клиент не передаёт порядок при чтении. Если `position` у двух строк совпал, порядок по UUID стабилен между вызовами.

История статусов в этот метод не входит. Её отдаёт только метод смены статуса. Клиент экрана заказа, которому нужна история, вызывает оба метода. Дублировать массив `history` в карточке заказа нельзя: наборы полей разойдутся.

Валюта в этом контуре одна, но поле `payment.currency` обязательно, чтобы контракт не подразумевал рубли молча. Появление другой валюты потребует новую колонку и новую версию метода, а не подмену кода внутри `RUB`.

Нулевая доставка кодируется числом 0, не `null`. `null` в `totals.delivery` — порча данных; метод всё равно отдаёт `null` и пишет в журнал. Клиент показывает прочерк только на `null`, ноль показывает как бесплатную доставку.

Скидка не бывает больше суммы товаров и доставки в нормальных данных. Если в базе больше, `totals.total` может выйти отрицательным. Метод знак не меняет. Исправление такой строки — отдельная операция поддержки, не этот GET.

Комментарий курьеру и комментарий покупателя — разные поля. Их нельзя склеивать. Пустой комментарий в базе хранится как `null` и так же уходит в JSON. Пустая строка в базе при чтении тоже становится `null`, чтобы у клиента была одна проверка.

Баллы `loyaltyPoints` до появления таблицы всегда `null` и всегда присутствуют. Ноль появится только когда таблица будет и у покупателя не будет начислений. До этого ноль не используется, чтобы не путать «программы нет» и «баллов нет».

## Метод POST /orders — создать заказ

### Общее описание

Метод создаёт заказ из корзины, которую клиент уже собрал на своей стороне. Сервер не хранит черновик корзины. В теле приходят покупатель, доставка, позиции и способ оплаты. В ответе — идентификатор созданного заказа, его номер, статус `created` и сумма к оплате.

Метод доступен только авторизованному покупателю. Сотрудник поддержки этим методом заказ не создаёт. Гость без авторизации получает HTTP 401. Этот код назван здесь явно: без авторизации заказ не создаётся, в отличие от чтения.

Идемпотентность задаёт заголовок `Idempotency-Key`. Повтор того же ключа от того же покупателя в течение 24 часов возвращает уже созданный заказ и HTTP 200, а не второй заказ. Если ключ тот же, а тело другое, ответ HTTP 409 «Ключ идемпотентности уже использован с другим телом».

### Доступы и ограничения

- Нужна авторизация покупателя.
- Не больше 50 позиций в одном заказе.
- Количество каждой позиции от 1 до 99.
- Сумма заказа после скидки больше нуля.
- Промокод необязателен. Неизвестный промокод — HTTP 400, заказ не создаётся.

### Запрос

Method type: POST BaseURL: https://api.shop.example API name: public API version: v1 Method name: orders

Пример запроса:

1 POST https://api.shop.example/public/v1/orders

Тело запроса — JSON. Query-параметров нет.

Заголовок `Idempotency-Key` обязателен. Это строка от 8 до 64 символов, её придумывает клиент. Заголовок `Authorization` обязателен, формат общий для системы и в этом методе не раскладывается.

### Пример запроса

```json
{
  "customer": {"name": "Анна Смирнова", "email": "anna@example.com", "phone": "+79990000000"},
  "delivery": {"method": "courier", "city": "Казань", "address": "ул. Баумана, 1", "postalCode": "420111"},
  "items": [{"sku": "MUG-01", "quantity": 2}],
  "paymentMethod": "card",
  "promoCode": null,
  "comment": "Позвонить за час"
}
```

### Пример ответа — успех

Код HTTP: 200

```json
{
  "id": "6b1f4c2a-9d0e-4a11-8c33-1a2b3c4d5e6f",
  "number": "A-10442",
  "status": "created",
  "totals": {"total": 213000},
  "paymentUrl": "https://pay.shop.example/invoice/6b1f4c2a"
}
```

Повтор с тем же ключом идемпотентности и тем же телом возвращает тот же объект и тоже HTTP 200. Отдельного кода «уже создан» нет.

### Пример ответа — нет авторизации

Код HTTP: 401

```json
{"errorMessage": "Требуется авторизация"}
```

### Пример ответа — неверное тело

Неизвестный артикул, количество вне диапазона, пустой список позиций, неверный город, промокод не найден или итог не больше нуля.

Код HTTP: 400

```json
{"errorMessage": "Тело заказа не прошло проверку"}
```

Текст в `errorMessage` общий. Какое именно поле не прошло проверку, метод в этой версии не возвращает. Это сознательное ограничение, а не пробел таблицы.

### Пример ответа — конфликт ключа

Код HTTP: 409

```json
{"errorMessage": "Ключ идемпотентности уже использован с другим телом"}
```

### Пример ответа — сервис недоступен

Код HTTP: 503

```json
{"errorMessage": "Сервис временно недоступен"}
```

### Основной сценарий

1. Проверить заголовок `Authorization`. Если его нет, вернуть HTTP 401 «Требуется авторизация».
2. Проверить `Idempotency-Key`. Если заголовка нет или длина вне 8–64, вернуть HTTP 400 «Тело заказа не прошло проверку».
3. Найти ранее созданный заказ с этим ключом и этим покупателем. Если найден и тело совпало, вернуть его и HTTP 200. Если найден и тело отличается, вернуть HTTP 409.
4. Проверить позиции: массив от 1 до 50 элементов, у каждой `sku` есть в каталоге и каталог отдаёт цену, `quantity` от 1 до 99.
5. Проверить доставку. Для `courier` обязательны `city`, `address`, `postalCode`. Для `pickup` обязателен `address` пункта, `postalCode` можно не передавать.
6. Если передан `promoCode`, найти его и посчитать скидку. Неизвестный код — HTTP 400, заказ не писать.
7. Посчитать итог. Если он не больше нуля, HTTP 400.
8. Записать `order`, `order_item`, `delivery`, `payment` в одной транзакции. Статус заказа — `created`. Оплата ещё не проведена: `payment.paid` ложно, `paymentUrl` ведёт на страницу оплаты.
9. Вернуть HTTP 200 и объект из таблицы ответа.

### Правила, которые нельзя сократить

Имя покупателя в теле создания — одна строка `customer.name`. Сервер сам делит её на фамилию и имя по первому пробелу: первое слово — фамилия, остаток — имя. Если пробела нет, фамилия пустая, вся строка — имя. Обратное склеивание при чтении описано в методе получения заказа.

Почта и телефон обязательны при создании, даже если потом гость их не увидит. Формат почты — наличие символа `@` и точки в домене. Формат телефона — от 10 до 15 цифр, ведущий `+` допустим. Буквы в телефоне — HTTP 400.

`delivery.method` принимает только `courier` и `pickup`. Другое значение — HTTP 400. Город — непустая строка до 80 символов. Адрес — непустая строка до 200 символов. Индекс — строка из 6 цифр для курьера. Для самовывоза индекс не проверяется и в базе может остаться пустым.

Позиция при создании содержит только `sku` и `quantity`. Цену и название клиент не присылает: их берёт сервер из каталога в момент создания и сохраняет в `order_item`, чтобы позднее изменение каталога не меняло уже созданный заказ. Неизвестный `sku` — HTTP 400 на весь заказ, частичное создание не делается.

`paymentMethod` — `card` или `invoice`. Для карты в ответе есть `paymentUrl`. Для счёта `paymentUrl` тоже есть: это ссылка на счёт, не на карточную форму. Поле в обоих случаях обязательно в ответе.

`promoCode` необязателен. Пустая строка считается так же, как отсутствие поля: скидки нет, ошибки нет. Код сравнивается без учёта регистра и хранится в заказе в верхнем регистре.

`comment` необязателен, до 500 символов. Более длинный комментарий — HTTP 400, а не обрезка.

`Idempotency-Key` не входит в JSON тела. Это заголовок. В таблице запроса он стоит отдельно от полей тела. Сравнение тел для идемпотентности — по каноническому JSON без пробелов и с отсортированными ключами объектов. Порядок позиций в массиве `items` значим: другой порядок считается другим телом.

Поле `source` в таблице тела помечено как будущее. Клиент может его не присылать. Если прислал, значение сохраняется, но витрина пока шлёт только `web`. Другие значения не отвергаются. Задачу на справочник источников заводят отдельно.

### Проверки создания, которые остаются в контракте

Каталог запрашивается по каждому `sku` отдельно, внутри одной серверной транзакции заказа. Если каталог не ответил, заказ не создаётся и клиент получает HTTP 503 «Сервис временно недоступен», а не HTTP 400. Недоступность каталога не является ошибкой тела.

Цена из каталога копируется в `order_item.price` до расчёта скидки. Скидка промокода применяется к итогу товаров, а не к каждой строке. Строка хранит цену без скидки. Так повторное чтение заказа показывает ту же цену, что видел покупатель в корзине, а скидка видна один раз в `totals.discount`.

Промокод с истёкшим сроком обрабатывается как неизвестный: HTTP 400 «Тело заказа не прошло проверку». Отдельной фразы про срок нет. Код, который ещё не наступил по дате начала, тоже неизвестен.

Лимит 50 позиций считается по элементам массива, а не по сумме `quantity`. Две строки с одним `sku` — две позиции. Сервер их не сливает. Если клиент прислал один артикул дважды, в заказе будут две строки, обе с ценой каталога на момент вызова.

Количество 0 и отрицательное количество — HTTP 400. Дробное количество не принимается: тип поля целое. Строка вместо числа — HTTP 400. Число в кавычках — тоже HTTP 400, приведения типов нет.

Самовывоз не требует индекса, но требует непустой `address`. Адрес пункта клиент копирует из справочника пунктов. Сервер справочник пунктов в этой версии не проверяет: несуществующий адрес самовывоза будет сохранён. Проверка пункта — отдельная задача, в этот метод она не входит.

Для курьера пустой индекс, индекс короче или длиннее 6 цифр и индекс с буквами — HTTP 400. Пробелы внутри индекса не удаляются.

Имя короче 2 символов после отбрасывания пробелов по краям — HTTP 400. Имя длиннее 120 символов — HTTP 400. Сервер не приводит регистр букв.

Телефон перед проверкой длины теряет пробелы, дефисы и скобки. Ведущий `+` можно оставить один. Второй `+` — HTTP 400. Буквы — HTTP 400.

Почта без `@` или с пробелом — HTTP 400. Два `@` — HTTP 400. Регистр почты сохраняется как прислал клиент, поиск дубля покупателя по почте в этом методе не делается: каждый вызов пишет заказ на уже авторизованного покупателя, а поля `customer.name`, `customer.email` и `customer.phone` обновляют карточку этого покупателя.

Обновление карточки покупателя происходит в той же транзакции, что и заказ. Если транзакция откатилась, карточка не меняется. Повтор идемпотентного запроса карточку второй раз не перезаписывает: возвращается уже созданный заказ, даже если карточка с тех пор изменилась другим вызовом.

Канонизация тела для сравнения ключа идемпотентности не включает заголовки. Смена `Authorization` при том же ключе и том же теле другим покупателем — это другой покупатель, ключ у него свой. Совпадение ключей разных покупателей допустимо и не считается конфликтом.

`paymentUrl` собирается из идентификатора заказа и не хранится колонкой. В маппинге так и сказано. При повторе идемпотентного вызова ссылка строится заново и обязана совпасть с первой, потому что идентификатор заказа тот же.

Номер заказа выдаёт последовательность базы. Дыры в номерах допустимы, если транзакция откатилась после взятия номера. Клиенту дыры не объясняются.

Поле `source`, если передано, обрезается по пробелам по краям и сохраняется как есть, до 32 символов. Длиннее — HTTP 400. Пустая строка сохраняется как `null`.

Создание не резервирует остаток на складе. Наличие проверяет уже переход в `assembling` вне этого метода. Поэтому успешный POST ещё не обещает, что товар поедет. Это написано здесь, чтобы клиент витрины не показывал «заказ собирается» сразу после HTTP 200.

Ссылка `paymentUrl` живёт, пока заказ в статусе `created`. После оплаты метод получения заказа её не возвращает: в карточке чтения этого поля нет. Держать оплату по старой ссылке после статуса `paid` платёжный контур не должен, но сам POST ссылку не отзывает.

Если в массиве `items` нет поля `sku` или нет `quantity`, весь заказ отклоняется с HTTP 400. Остальные позиции не сообщаются отдельно. Ответ не содержит списка ошибок по строкам.

Числовые поля тела не принимают `null`. Обязательное число без значения — отсутствующее поле, и это HTTP 400. Необязательных чисел в теле создания нет.

## Метод PATCH /orders/{orderId} — изменить статус заказа

### Общее описание

Метод переводит заказ в следующий статус. Его вызывает не витрина покупателя, а внутренний контур: оплата, склад и доставка. Покупатель этим методом статус не меняет. Если вызывающий не сотрудник соответствующего контура, ответ HTTP 403 «Недостаточно прав».

Допустимые переходы:

- `created` → `paid` или `cancelled`
- `paid` → `assembling` или `cancelled`
- `assembling` → `shipped` или `cancelled`
- `shipped` → `delivered`
- `delivered` и `cancelled` дальше не переводятся

Любой другой переход — HTTP 409 «Переход статуса недопустим». Заказ при этом не меняется.

Причина `reason` обязательна только для перехода в `cancelled`. Для остальных переходов причину можно не передавать. Комментарий сотрудника необязателен всегда.

### Доступы и ограничения

- Нужна авторизация сотрудника контура, который владеет целевым статусом.
- Покупатель получает HTTP 403.
- Неизвестный заказ — HTTP 404 «Заказ не найден». Черновик этим методом тоже не находится.

### Запрос

Method type: PATCH BaseURL: https://api.shop.example API name: public API version: v1 Method name: orders/{orderId}

Пример запроса:

1 PATCH https://api.shop.example/public/v1/orders/{orderId}

Пример:

1 PATCH https://api.shop.example/public/v1/orders/6b1f4c2a-9d0e-4a11-8c33-1a2b3c4d5e6f

Query-параметров нет. Тело — JSON со статусом.

### Пример запроса

```json
{"status": "cancelled", "reason": "buyer", "comment": "Покупатель отказался до сборки"}
```

### Пример ответа — успех

Код HTTP: 200

```json
{
  "id": "6b1f4c2a-9d0e-4a11-8c33-1a2b3c4d5e6f",
  "status": "cancelled",
  "updatedAt": "2026-10-08T12:00:00Z",
  "history": [
    {"status": "created", "at": "2026-10-08T09:00:00Z", "actor": "customer"},
    {"status": "cancelled", "at": "2026-10-08T12:00:00Z", "actor": "support"}
  ]
}
```

### Пример ответа — нет прав

Код HTTP: 403

```json
{"errorMessage": "Недостаточно прав"}
```

### Пример ответа — не найдено

Код HTTP: 404

```json
{"errorMessage": "Заказ не найден"}
```

### Пример ответа — недопустимый переход

Код HTTP: 409

```json
{"errorMessage": "Переход статуса недопустим"}
```

Сюда же относится отмена без `reason` и неизвестное значение `status`. Отмена без причины не является HTTP 400: правило перехода едино, и клиент контура обрабатывает один код конфликта.

### Пример ответа — неверный идентификатор

Если `orderId` не UUID, тело не читается.

Код HTTP: 400

```json
{"errorMessage": "Неверный формат идентификатора заказа"}
```

### Пример ответа — сервис недоступен

Код HTTP: 503

```json
{"errorMessage": "Сервис временно недоступен"}
```

### Основной сценарий

1. Проверить, что `orderId` — UUID. Иначе HTTP 400 «Неверный формат идентификатора заказа».
2. Проверить авторизацию сотрудника. Покупатель и гость — HTTP 403 «Недостаточно прав».
3. Найти заказ. Нет записи или статус `draft` — HTTP 404 «Заказ не найден».
4. Прочитать текущий статус и запрошенный `status`. Если пары нет в списке переходов, HTTP 409 «Переход статуса недопустим».
5. Если целевой статус `cancelled` и `reason` пуст, HTTP 409 «Переход статуса недопустим».
6. Дописать строку в `order_status_history`: прежний статус не затирать. Обновить `order.status` и `order.updated_at`.
7. Вернуть HTTP 200, новый статус, время обновления и всю историю переходов от создания до текущего.

### Правила, которые нельзя сократить

`status` в теле — целевой статус, не текущий. Текущий метод берёт из базы. Клиент не присылает «ожидаемый текущий статус»: оптимистической блокировки в этой версии нет. Два сотрудника могут отправить два допустимых перехода подряд. Оба применятся по очереди, если каждый был допустим на момент своей транзакции. Если второй переход уже недопустим, он получит HTTP 409.

`reason` — одно из `buyer`, `payment`, `stock`, `delivery`. Другое значение при отмене — HTTP 409, не HTTP 400. Для переходов кроме отмены поле игнорируется, даже если прислано. В историю причина пишется только для `cancelled`.

`comment` — необязательная строка до 500 символов. Более длинный комментарий — HTTP 409 по тому же правилу, что и прочие нарушения перехода. Обрезки нет.

`actor` в истории метод не принимает в теле. Его выводит сервер из контура вызывающего: `payment`, `warehouse`, `delivery` или `support`. В ответе это строка, не идентификатор сотрудника. Имя сотрудника в контракт не входит.

История `history` упорядочена по времени от старого к новому. Первая запись — создание заказа, даже если этот метод создание не выполнял: строка появляется в методе создания со статусом `created` и актором `customer`. Этот метод только дописывает.

`updatedAt` — время именно этого перехода, оно совпадает с `at` последней записи истории. Если часы базы и приложения расходятся, верным считается время базы.

Поле `notifyCustomer` в таблице запроса — будущее. Если его не прислали, покупателю уходит прежнее письмо о смене статуса. Если прислали `false`, письмо не ставится в очередь. Задачу на шаблоны писем ведут отдельно, поле из контракта не убирают.

Повтор того же целевого статуса, который уже установлен, — HTTP 409. Идемпотентного «уже в этом статусе» с кодом 200 нет, чтобы клиент контура не путал успех перехода с повторной доставкой сообщения.

### Проверки перехода, которые остаются в контракте

Транзакция перехода блокирует строку `order` на запись. Второй параллельный вызов ждёт. После ожидания он читает уже новый статус и заново проверяет таблицу переходов. Поэтому два одинаковых перевода в `paid` не проходят оба: второй видит `paid` и получает HTTP 409.

Контур вызывающего определяется по роли в авторизации, не по телу. Роль `payment` может ставить только `paid`. Роль `warehouse` — только `assembling` и `shipped`. Роль `delivery` — только `delivered`. Роль `support` может ставить `cancelled` из разрешённых исходных статусов и не может двигать заказ по складу. Чужая роль на чужой целевой статус — HTTP 403 «Недостаточно прав», даже если переход в графе сам по себе есть.

Отмена поддержкой разрешена из `created`, `paid` и `assembling`. Из `shipped` отмена этим методом запрещена: посылка уже ушла, HTTP 409. Возврат после доставки этим методом не оформляется.

При переходе в `paid` сервер дополнительно требует, что в `payment` есть строка и `payment.method` заполнен. Если оплаты нет, это порча данных созданного заказа: HTTP 409, а не 500. Платёжный контур не чинит отсутствующую оплату этим методом.

При переходе в `shipped` комментарий можно использовать для номера отправления, но отдельного поля трек-номера в контракте нет. Кладка трека в `comment` — временное правило склада. Поле трека не добавляется молча.

История пишется всегда, включая неуспешные попытки? Нет. В `order_status_history` попадает только совершённый переход. Отказы 403, 404, 409 и 400 историю не пополняют.

Время `updatedAt` берётся из базы в момент update, одним значением и для `order.updated_at`, и для `order_status_history.created_at`. Клиент не присылает время. Если в теле есть лишнее поле `updatedAt`, оно игнорируется, ошибки из-за лишнего поля нет. Неизвестные поля тела, кроме перечисленных в таблице, игнорируются.

`notifyCustomer` принимает только JSON boolean. Строки `true` и `false` — HTTP 409, как и прочие нарушения правил перехода. Отсутствие поля означает прежнее поведение: письмо ставится в очередь. `true` тоже ставит письмо. `false` не ставит. Очередь писем при HTTP 409 и HTTP 403 не трогается.

Ответ содержит всю историю, не только новую строку. Клиенту контура нельзя кэшировать историю между вызовами как полную: другой контур мог дописать переход. Каждый успешный ответ самодостаточен.

Порядок записей истории при одинаковом времени не ожидается: время базы для двух переходов одного заказа различается, потому что вторая транзакция ждёт первую. Стабильный запасной порядок, если время всё же совпало, — по возрастанию `order_status_history.id`.

Причина отмены в истории ответа есть только у записи со статусом `cancelled`. У остальных записей ключ `history[].reason` присутствует и равен `null`. Так клиент не отличает старые строки без колонки от новых.

Актор `customer` встречается только у первой записи, её пишет метод создания. Этот метод актора `customer` не ставит. Если поддержка отменяет заказ, актор — `support`, даже если причину выбрал покупатель по телефону: в контракте актор — контур учётной записи, а не инициатор в жизни.

Длина `comment` считается в символах Unicode, не в байтах. 500 символов ещё допустимы, 501 — HTTP 409. Пробелы по краям не обрезаются и входят в длину.

Повторный PATCH с тем же телом после успеха не является идемпотентным. Второго заголовка ключа у метода нет. Повтор получит HTTP 409, потому что статус уже целевой. Клиент контура, который повторяет доставку сообщения, должен считать 409 на уже выполненном переходе успехом у себя, но сервер код 200 за это не отдаёт.

Черновик не переводится в `created` этим методом. Создание черновика в контракте сервиса отсутствует. Вызов по идентификатору черновика выглядит как отсутствующий заказ.

Оплата, которая пришла после отмены, этим методом не возвращает заказ в `paid`. Платёжный контур получает HTTP 409 и разбирает деньги своим процессом. Контракт PATCH не содержит компенсации.

Склад не может перескочить из `paid` сразу в `shipped`. Нужен отдельный вызов в `assembling`, затем вызов в `shipped`. Один запрос с целевым статусом через шаг граф не сокращает.

Доставка не ставит `delivered` из `assembling`. Только из `shipped`. Если склад не отметил отгрузку, доставка получает HTTP 409 и не дописывает историю.

Поддержка не меняет статус на `paid`, даже если покупатель принёс квитанцию. Оплату проводит роль `payment`. Иначе в истории появляется актор, которого граф денег не ждёт.

Комментарий при отмене сохраняется в той же строке истории, что и `reason`. В ответе комментария нет: таблица ответа его не содержит. Прочитать комментарий этим методом нельзя. Его видит только внутренний журнал смены статуса, и даже туда текст комментария не попадает, туда пишутся только статусы и код.

Если роль сотрудника содержит несколько контуров сразу, достаточно одной подходящей роли на целевой статус. Лишние роли не мешают. Отсутствие всех ролей — HTTP 403.

Значение `status` сравнивается точно, с учётом регистра. `Paid` и `PAID` — неизвестный переход, HTTP 409. Пробелы по краям не обрезаются.

Пустое тело JSON `{}` — нет `status`, это HTTP 409, потому что переход не из чего строить. Тело не JSON — HTTP 400 «Неверный формат идентификатора заказа» сюда не относится: идентификатор уже проверен. Не-JSON тело даёт HTTP 409 «Переход статуса недопустим», чтобы у контура остался один код на испорченное тело после годного UUID. Это жёсткое правило, его не смягчают отдельным текстом.

Массив `history` в успешном ответе содержит не меньше двух записей: создание и текущий переход. Одной записи быть не может, потому что в `created` этим методом не входят, а черновик не виден. Клиент может опираться на длину массива как на признак, что ответ именно этого метода, а не пустая заготовка.

### Маппинг данных

Для запроса:

| Параметр | Описание | Обязательность | Тип данных | В БД |
| --- | --- | --- | --- | --- |
| {orderId} | UUID заказа в пути | Да | UUID | order.id |
| status | Целевой статус | Да | string | order.status |
| reason | Причина отмены: buyer, payment, stock, delivery | Нет | string | order_status_history.reason |
| comment | Комментарий сотрудника до 500 символов | Нет | string | order_status_history.comment |
| notifyCustomer | Письмо покупателю. Надо добавить шаблоны писем. Если поля нет, письмо отправляется по старому правилу. | Нет | boolean | нет колонки |

Для тела ответа:

| Параметр в JSON | Описание | Обязательность | Тип данных в JSON | В БД |
| --- | --- | --- | --- | --- |
| id | UUID заказа | Да | uuid | order.id |
| status | Статус после перехода | Да | string | order.status |
| updatedAt | Время перехода | Да | string (timestamp) | order.updated_at |
| history | История статусов от старого к новому | Да | array | order_status_history |
| history[].status | Статус в этой записи | Да | string | order_status_history.status |
| history[].at | Время записи | Да | string (timestamp) | order_status_history.created_at |
| history[].actor | Контур, который сделал переход | Да | string | order_status_history.actor |
| history[].reason | Причина, null если это не отмена | Нет | string | order_status_history.reason |

### Журнал

Писать идентификатор заказа, прежний статус, новый статус и код ответа. Комментарий сотрудника в журнал не писать.
