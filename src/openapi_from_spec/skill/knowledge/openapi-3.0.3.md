# OpenAPI 3.0.3 для задачи openapi

Документ самодостаточен. Сеть для этих правил не нужна. Модель пишет YAML одного фрагмента. Код потом сшивает `paths` и `components` нескольких фрагментов.

## Корень

- `openapi`: строка `3.0.3`
- `info.title` и `info.version`. `info.version` пиши строкой в кавычках, например `"1.0.0"`
- `paths`: объект. Ключ — путь, значение — методы `get`, `post`, `put`, `patch`, `delete`, `head`, `options`

`servers` пиши, только если адрес или плейсхолдер есть во фрагменте. Схему безопасности не выдумывай.

Запись `{base_url}/claim/individual` даёт путь `/claim/individual` и сервер:

```yaml
servers:
  - url: "{base_url}"
    variables:
      base_url:
        default: /
```

Имя плейсхолдера бери из фигурных скобок фрагмента. Готовый путь из ТЗ не дополняй префиксом `/api/v1`. Если во фрагменте есть полный адрес метода, путь и сервер берутся из него: короткий заголовок с тем же методом его не заменяет. Префикс сервера в пути не повторяй: если сервер уже кончается на `/api/v1`, пример `POST /api/v1/users` даёт путь `/users`. Число в конце примера (`PUT /transactions/1`) — path-параметр `{id}`, а не часть пути без параметра. Если во фрагменте только имя вроде `accountBalances` и нет пути, путь — kebab-case во множественном числе. Версию в начало пути ставь только если она названа во фрагменте: `/api/v1/account-balances`. Если версии нет, префикс не выдумывай.

## Операция

Нужны `operationId`, `summary`, `tags` и `responses`. `summary` — фраза из фрагмента. `tags` — один домен в PascalCase по имени ресурса: `Orders`. Добавляй `description`, `parameters`, `requestBody`, только если они есть во фрагменте.

`operationId` — глагол и имя ресурса в camelCase: `getAccountBalances`. Имя path-параметра в него не входит: `GET /recipes/{recipeId}` даёт `getRecipes`, не `getRecipesRecipeId`. Во всём документе `operationId` уникален. Если метод выведен из смысла фрагмента, а не из глагола HTTP, добавь `x-method-origin: inferred`.

## Параметр и схема

`name`, `in` (`query`, `path`, `header`, `cookie`), `schema`, `description`. Параметр пути всегда `required: true`.

`type` — только `string`, `number`, `integer`, `boolean`, `array` или `object`. Слово из ТЗ в `type` не пиши.

| Как в ТЗ | OpenAPI |
| --- | --- |
| String, Text, Строка | string |
| String (url), string (url) | string, format uri |
| String(12) | string и `maxLength: 12` |
| UUID | string, format uuid |
| Date, Дата | string, format date |
| DateTime, Date-Time, Дата и время, string (timestamp) | string, format date-time |
| Boolean, Bool, Логический, Булево | boolean |
| Integer, Int, Целое | integer |
| Long, Int64 | integer, format int64 |
| Number, Decimal, Число | number |
| Double | number, format double |
| Float | number, format float |
| Object, Объект | object |
| Array, List, Set, Массив, Список | array |
| File, Binary, Файл | string, format binary |

У каждого `array` есть `items`. Если ячейка типа говорит только `array`, а в примере у этого поля читаются строки, например `["Салаты", "Обед"]`, у `items` тип `string`. Другие свойства из обрезанного примера не добавляй. Вложенные строки `└─` — свойства объекта или элемента массива.

Колонка «Максимальная длина» у строки — `maxLength`. У целого и числа — `x-tz-max-length`, не `maxLength`. У `List` или `Array` строк длина относится к `items`, не к самому массиву. Запись `String(12)` даёт `maxLength: 12`, даже если колонка длины пустая.

Обязательность пиши, если ячейка не пустая:

- `Да`, `М`, `+` и кириллическая `О` — `required: true`
- `Нет`, `Н` и латинская `O` — `required: false`
- пустая ячейка — ключ `required` не ставь и поле не включай в массив `required` схемы
- ячейка из глаголов `post`, `put`, `get`, `delete` — поле обязательно в запросе этих методов, но не в `required` схемы ответа

У схемы тела и вложенного объекта `required` — массив имён с признаком true. Имена с false и с пустой ячейкой в этот массив не входят. Пустая ячейка относится к самой строке, а не к детям. Если у объекта `author` или у массивов `ingredients` и `steps` ячейка пустая, этих имён нет в `required` родителя, даже когда каждое вложенное поле обязательно.

Повтор ключа в строке метода (`accounts=a&accounts=b`) для массива: `style: form` и `explode: true`.

Объект с несколькими полями клади в `components/schemas` и ссылайся через `$ref`. Имя схемы — PascalCase: `UserResponse`, `CreateUserRequest`. Одну и ту же схему второй раз inline не копируй. В 3.0.3 рядом с `$ref` не ставь другие поля.

`example` у поля, параметра или ответа пиши только если этот JSON есть во фрагменте и разбирается. Пример, которого в ТЗ нет, не сочиняй. Таблица полей важнее примера: обрезанный пример с номерами строк не задаёт свойства. Поля ответа в этом случае бери из таблицы, а не из примера. Имя и формат ячейки тоже важнее примера. Поле `classRecord` с форматом `ClassRecord` — объект `$ref` на `ClassRecord`, не массив и не ключ `classRecords`. Если пример спорит с этим именем или форматом, его не копируй. Поле из таблицы, которое есть в целом JSON-примере, остаётся в схеме: пустая ячейка делает его необязательным, а не отсутствующим. Маркеры `*` в `description` не копируй.

## Ответ

У каждого элемента `responses` есть `description`. Для кода, названного во фрагменте, это дословная фраза из абзаца рядом с кодом. Если в примере есть `errorMessage` и он не противоречит абзацу, бери текст `errorMessage`. Заголовок раздела («Успех», «Не найдено», «Неверный формат запроса») не ставь, когда такая фраза есть. Если пример спорит с абзацем, в `description` пиши фразу абзаца, а сам пример в YAML не копируй. Не пиши слово `ok` и не подставляй сам код. Без `description` проверка 3.0.3 не проходит.

Если таблицы ответа нет, всё равно запиши `200` и без `content`, когда тела в таблице нет. Код `200` здесь не выдумка полей, а обязательная оболочка операции. Если у успеха нет своей фразы, а заголовок раздела — только «Успех», в `description` поставь `summary` операции, не слово «Успех». Тело ответа добавляй только по таблице или примеру фрагмента.

Код, названный во фрагменте, запиши с его фразой, в том числе 409, 422 или 503. Запись `(422 Unprocessable Entity)` и `HTTP/1.1 422` — такой же код, как «Код HTTP». В `description` поставь текст `error` или `errorMessage` из примера этого кода. Дополнительно закрой набор 400, 401, 404, 500. Код из этого набора, которого во фрагменте нет, — общий шаблон, без тела. Если фрагмент пишет, что сервис использует следующие HTTP-коды, или приводит таблицу кодов ответа, список закрытый: 403 и 503 из этой таблицы запиши с описанием из неё, а шаблон 500 не добавляй, когда в таблице вместо него 503.

```yaml
components:
  responses:
    BadRequest:
      description: Некорректный запрос
      x-origin: skill-template
    Unauthorized:
      description: Требуется аутентификация
      x-origin: skill-template
    NotFound:
      description: Ресурс не найден
      x-origin: skill-template
    InternalError:
      description: Внутренняя ошибка сервиса
      x-origin: skill-template
```

В операции ссылка без соседних полей:

```yaml
"400":
  $ref: "#/components/responses/BadRequest"
```

Фразу из ТЗ шаблоном не заменяй. Если 400 во фрагменте назван, у этого кода `description` из фрагмента, а не `BadRequest`. Компонент, на который ведёт `$ref`, объяви в `components/responses` того же документа.

## Если проверка вернула oneOf

Текст ошибки не называет поле. Сначала проверь два места: у ответа нет `description`; в `type` осталось слово ТЗ вроде `UUID`, `Decimal`, `Float` или `File`.

## Чего не добавлять

Не добавляй поля, заголовки авторизации и коды ответов вне набора 400, 401, 404, 500, если их нет во фрагменте. Шаблон этого набора не содержит свойств из ТЗ. Не используй возможности 3.1: массив в поле `type`, `webhooks`, поля рядом с `$ref`.
